There are two robots

5618 and 6494 are not the same robot. Device names on this page are shared, but motor directions and tuned values are per‑robot — 6494’s rear wheels spin the opposite way from 5618’s. Code reads which robot it is from the active config name, so the Driver Station config must start with 6494 or 5618 (6494-practice counts). If it does not, WhichRobot throws and the robot refuses to INIT rather than guessing and driving the wrong way.

Things that bite

Each of these has cost the team time at least once.

There is no turretEncoder device, and there cannot be

The turret’s REV Through Bore encoder plugs into lf’s spare encoder connector, so the SDK reads it through the lf motor. There is nothing to add to the config.

REV Through Bore→ lf spare encoder port (CH M1)→ hardwareMap.get(DcMotorEx, "lf")→ Turret.java

Two rules keep sharing that port safe:

  1. lf stays in RUN_WITHOUT_ENCODER (the default). In RUN_USING_ENCODER or RUN_TO_POSITION, the hub would regulate a drive wheel from the turret’s position.
  2. Nobody calls STOP_AND_RESET_ENCODER on lf, which would zero the turret mid‑match.

The two shooter motors are on different hubs

shooterRight on CH M2, shooterLeft on EH M2. Each hub runs its own velocity PIDF locally, so each wheel regulates itself fine, and the split spreads current draw. But if the two ever report speeds that disagree, cross‑hub command skew is the first suspect — see docs/flywheel-rpm-gap.md.

Direction lives in code, not in the config

Never reverse a motor in the Driver Station config. Code already sets every direction, and the two cancel out — the motor spins the original way and nothing looks wrong.

Direction is set in three different places, which is the part that catches people:

MotorDirectionSet where
shooterRightREVERSERobotHardware.init()
collectorFORWARDRobotHardware.applyCollectionDirections()
indexerFORWARDRobotHardware.applyCollectionDirections()
lf lr rf rrper robotConstants.driveConstants()

collector is FORWARD, and that correction cost the team real time. It was recorded as REVERSE on 2026‑10‑29, but the check that "confirmed" it had actually read the motors raw at their FORWARD default. So the collector ran backwards in everything built on RobotHardware — Shooter Test, DriveTeleOp and the autos — until it turned up on 6494 on 2026‑11‑05. FORWARD pulls pieces in; indexer FORWARD feeds up to the shooter. Confirmed on 6494, still unchecked on 5618.

REV digital sensors can land on the odd pin

A switch wired into digital pair 0‑1 sometimes configures as port 1 rather than port 0. turretHome reports on either, so it does not matter there — but check it first if a digital device reads nothing.

Stop thumb‑typing the config

The Driver Station stores each robot configuration as an XML file on the Robot Controller, under /sdcard/FIRST/settings/. Build it by hand once, and from then on it is a file you can push to any robot. These steps run in order — step 4 is the one that pays for the other four.

  1. Build the config once on the Driver Station

    From the device map above. This is the only hand‑typing anyone should ever have to do.

  2. Connect to the Robot Controller

    USB‑C to the Control Hub, or over the robot’s wifi:

    adb connect 192.168.43.1:5555
  3. Find the file name

    It is named whatever you called the config.

    adb shell ls /sdcard/FIRST/settings/
  4. Pull it into the repo so it is version controlled
    adb pull /sdcard/FIRST/settings/<YourConfigName>.xml docs/robot-config/
  5. Push it to any robot from then on
    adb push docs/robot-config/<YourConfigName>.xml /sdcard/FIRST/settings/

    Then on the Driver Station: Configure Robot → the config appears in the list → Activate. A rebuilt Control Hub becomes one command away from a working config, and a wiring change shows up as a reviewable diff instead of a rumour.

Do not use hardware2025.xml as a template

TeamCode/src/main/res/xml/hardware2025.xml is not a usable config. Its format (<RobotConfiguration>, MotorType.REV_HD_20_1) is not what the FTC SDK reads, and its device names (exampleServo, leftOdo) match nothing in the code. It was never loadable — which is probably why last season still got typed in by hand.

adb lives at C:\Users\<you>\AppData\Local\Android\Sdk\platform-tools\adb.exe.
